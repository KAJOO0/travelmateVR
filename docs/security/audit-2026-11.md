# Security audit — November 2026

Structured code-based review against OWASP Top 10 / ASVS-style categories, per the platform
optimization directive §12. This is a **static code and configuration review**, not a live
penetration test — findings are classified honestly, and nothing here is claimed as "fully
secure" on the strength of this review alone.

Severity: **Critical / High / Medium / Low / Informational**. Status: **Already implemented /
Newly implemented / Improved / Not implemented / Requires further investigation**.

## Findings

### 1. Dependency vulnerabilities — Low (runtime), Informational (dev tooling)
**Status: Requires monitoring, not urgent.**
`npm audit` reports 83 vulnerabilities (4 critical, 39 high, 37 moderate, 3 low) — but
`npm audit --omit=dev` reports **zero**. Every flagged vulnerability traces to
`@aws-amplify/backend-*` packages (the deploy-time CLI tooling, a `devDependency`), rooted in
transitive `zod`/`glob`/`handlebars` version conflicts — never shipped to a visitor's browser.
This is a supply-chain hygiene item for whoever runs deploys, not a live-site risk. Not forcing
`npm audit fix --force` here deliberately — it would shift AWS's own CLI tooling versions and
risks re-breaking the deploy pipeline we just stabilized, for packages that never reach
production anyway. Recommendation: monitor for upstream AWS fixes, don't force now.

### 2. Historical secret in git history — Low, remediated by removal
**Status: Already resolved (incidentally, via the project restructure), informational only.**
Commit `8ae9a381` (Jul 2025, different author) added a `.env` file containing EmailJS service
and template IDs. These are not secret keys (EmailJS's actual security boundary is a separate
public key + domain restriction) — low sensitivity. The file is no longer tracked, and EmailJS
is no longer used anywhere in the current codebase. Git history itself isn't rewritten (not
warranted for this sensitivity level); flagging for completeness per the directive's explicit
ask to check for exposed credentials.

### 3. Progressive login lockout — Medium, not implemented server-side
**Status: Client-side only; directive explicitly requires server-side.** Already flagged last
session. `src/services/account.ts`'s `loginGuard` tracks failures in `localStorage`
(`tm.auth.guard`), applied in both mock and real mode. In real mode this means **the lockout
is cosmetic** — clearing browser storage or switching devices bypasses it entirely. See the
implementation directive below (§A) for the real fix.

### 4. Auth tokens in localStorage — Medium, inherent to the chosen auth library
**Status: Requires further investigation / accepted tradeoff.** Amplify Auth (v6) stores
Cognito tokens in `localStorage` by default; we didn't override this with a custom secure
storage adapter. This matters only if an XSS injection point exists — and the CSP shipped this
session allows `'unsafe-inline'` for `script-src` (necessary today for the one inline
theme-flash script in `index.html`; see `docs/security/http-headers.md`), which weakens CSP's
ability to block injected inline scripts if one ever got in. Actual injection surface is small
today: React escapes by default, and the only `dangerouslySetInnerHTML` use
(`src/components/ui/QrCode.tsx`) renders SVG generated by the `qrcode` library from geometric
path data, not raw user text — reviewed, not exploitable. Recommendation: the real fix is
tightening `script-src` to a nonce/hash (removing `'unsafe-inline'`), which is a build-pipeline
change, not a quick header edit — tracked as a follow-up, not done this pass to avoid risking a
live breakage from a mismatched hash.

### 5. `next` redirect parameter — Informational, not exploitable here
**Status: Reviewed, no action needed.** `SignInPage.tsx`'s `next = params.get('next')?.startsWith('/') ? ... `
check would, in a server-redirect context, be bypassable via `//evil.com` (which also starts
with `/`). Here it's used purely with React Router's client-side `navigate()`, which operates
through `history.pushState` and cannot navigate cross-origin regardless of the string passed —
not a real open redirect in this specific usage. Worth tightening anyway as defense-in-depth
if this value is ever reused in a server-redirect context later.

### 6. Database backups — Medium, now fixed
**Status: Newly implemented.** Point-in-time recovery (continuous backups, 35-day window) was
**disabled on all 12 DynamoDB tables** (both sandbox and production) — confirmed directly via
AWS, not assumed. Enabled on all of them this session. Table encryption at rest was already
correctly on (AWS-owned default key) — no action needed there.

### 7. IAM access key — Medium, known, deferred by prior agreement
**Status: Flagged, action pending.** `travelmatevr-cli-deploy` still holds `AdministratorAccess`
— appropriate for the deploy work done so far, not appropriate to leave indefinitely. Rotate or
scope down once you're confident no more infrastructure changes are imminent.

### 8. Client-side-only RBAC for admin/business/board — Medium/High, inherited scope gap
**Status: Not implemented (inherited from the earlier AWS-backend phase's explicit scope cut).**
`services/admin.ts`'s `canRead`/`canWrite` RBAC matrix is enforced only in the UI. Since the
admin/business/board backends are still mock/demo-only (no real data behind them yet), there's
no real data to actually leak via this gap today — but it means this RBAC provides **zero real
protection** and must not be mistaken for a security boundary. This is a known, previously
agreed-upon scope boundary, not a new finding, restated here for completeness per the
directive's explicit RBAC audit requirement (§13).

### 9. AI planner / search read local seed data, not the real catalogue — Informational
**Status: Pre-existing architectural inconsistency, not a security issue, worth knowing about.**
`services/ai.ts` and `services/search.ts` operate on `seedIndex` (the static seed arrays) even
in real-backend mode — only `catalog.ts` and `account.ts` were wired to the real backend. Not a
vulnerability, but means the AI planner and search results can diverge from what the real
catalogue pages show. Worth addressing in a future backend phase, not a security fix.

### 10. CSP / security headers, SEO noindex, data authorization rules, encryption at rest —
**Status: Already implemented / newly implemented this session**, see the main status report
for specifics. Guest-read/admin-write Amplify Data authorization was verified directly against
AWS (not just read from the schema file) back when the backend was first built: an
unauthenticated write attempt was rejected with "Not Authorized."
