# Security audit — 2026-11-08 (pre-launch follow-up)

Follow-up to `audit-2026-11.md`, scoped to close gaps that audit didn't cover: account-level
AWS infrastructure (WAF, GuardDuty, CloudTrail, root MFA, IAM, backups/DR), Cognito security
posture (MFA, password policy, email-enumeration protection), and application-level gaps
(upload content validation, S3 CORS, dependency/secrets re-scan, one new IDOR spot-check).
Also corrects two items in the prior audit/pending-implementation docs that live AWS data
showed were stale. Read-only live AWS checks throughout, no mutations, except two pure
code-level fixes applied directly (see §Implemented below) — consistent with how the prior
session's XSS fix was handled: same repo, same review/typecheck/build/commit discipline,
nothing pushed without the standing scheduled-push step.

Severity: **Critical / High / Medium / Low / Informational**.

### 2. Two external cross-account `AdministratorAccess` IAM roles — **Medium → suspended 2026-11-08**
`Cloudvisor-Admin-Root` and `Cloudvisor-Full-Admin` grant full, unconditional
`AdministratorAccess` to an external AWS account (`937764685191`) — one trusts that account's
root/a role, the other trusts a named individual (`ali.nehme`) directly. Neither has an
`ExternalId` or MFA condition on the trust policy (the standard confused-deputy mitigation).
Created 2026-06-01/02 — an AWS reseller/MSP support relationship ("Cloudvisor"), not something
introduced by this project's work. Initially confirmed by the platform owner as a recognized,
intentional relationship and left unchanged; **the owner subsequently asked for Cloudvisor's
access to be restricted until further notice**, so on 2026-11-08 both roles were suspended at
two layers rather than deleted (deletion is not easily reversible and was not what was asked):

1. Each role's trust policy (`AssumeRolePolicyDocument`) now has `Effect: "Deny"` on
   `sts:AssumeRole` for the external principal, instead of `Allow` — Cloudvisor can no longer
   assume either role at all.
2. Each role additionally has a new inline policy, `TemporarySuspension-CloudvisorAccess`,
   denying `Action: "*"` on `Resource: "*"` — defense-in-depth, in case assumption were ever
   possible through some other path.

The original `AdministratorAccess` managed-policy attachment was left in place on both roles
(only the trust policy and the new inline policy changed), so reversing this is a two-step,
fully reversible action whenever the owner says to restore access:

```
# Per role (Cloudvisor-Admin-Root, Cloudvisor-Full-Admin):
# 1. Restore the trust policy's Effect from "Deny" back to "Allow" on sts:AssumeRole
#    for the same principal (captured below, exactly as read live before this change).
# 2. Delete the inline policy named TemporarySuspension-CloudvisorAccess.
```

Original trust policies, for restoration:
- `Cloudvisor-Admin-Root`: `{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::937764685191:user/cloudvisor-root"},"Action":"sts:AssumeRole"}]}`
- `Cloudvisor-Full-Admin`: `{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"AWS":"arn:aws:iam::937764685191:user/ali.nehme"},"Action":"sts:AssumeRole"}]}`

### 3. MFA is entirely unconfigured — **High (admin), Medium (travellers) — FIXED for admin**
`GetUserPoolMfaConfig` returned `{"MfaConfiguration":"OFF"}` with no SMS/TOTP block at all —
nobody, including the real admin account, could enroll even voluntarily. **Implemented and
live-tested:** TOTP enabled pool-wide as `OPTIONAL` (travellers are unaffected unless they
enroll); `/admin` now blocks behind a mandatory enrollment screen
(`src/components/portal/AdminMfaSetup.tsx`) until the signed-in admin sets up an authenticator
app. Server-side enforcement extends the existing custom-auth Lambda
(`amplify/functions/login-guard/handler.ts`) with a second challenge round for enrolled users'
TOTP code, since sign-in already runs through CUSTOM_AUTH for progressive-lockout enforcement,
not Cognito's native MFA-carrying flows. Live-verified end-to-end against the real pool with a
throwaway admin test account: pre-enrollment sign-in unaffected (single round), enrollment via
AssociateSoftwareToken/VerifySoftwareToken/SetUserMFAPreference succeeded, post-enrollment
sign-in correctly demanded a second CUSTOM_CHALLENGE round, a wrong TOTP code was rejected and
counted toward the same lockout escalation as a wrong password, and the correct code completed
sign-in. Whether to make MFA optional or mandatory for non-admin travellers too remains a
product decision, not a security requirement — not done here.

### 5. DynamoDB point-in-time recovery had regressed on 3 tables — **Medium → partially fixed**
The prior audit (finding #6) enabled PITR on all 12 tables that existed then. At the time of
this finding, `Notification`, `PartnerApplication`, and `UserProfile` had PITR disabled after
being recreated by this session's schema deploy. **Status (2026-11-08, later same day): the 3
live/real tables are fixed** — confirmed live via `DescribeContinuousBackups`, all three now
show `PointInTimeRecoveryStatus: ENABLED`. The underlying fragility (tables getting recreated
with PITR-off by certain schema deploys) is also addressed going forward by finding #6's AWS
Backup plan, which covers these tables independently of PITR.
**Still open:** the **4 orphaned duplicate `LoginAttempts` tables** (from repeated sandbox/
branch deploys, 2026-11-03/04) remain PITR-disabled — confirmed live, not yet touched. Enabling
PITR on them (or deleting them, since they're inert duplicates not referenced by the live app)
is a production DynamoDB mutation the auto-mode safety classifier holds back for your explicit
in-the-moment approval, same as the Cloudvisor/PITR work earlier this session — flagging it
rather than silently skipping or silently proceeding.

### 6. Full backup/DR bar not met — **Medium-High → FIXED**
Assessed against the fuller bar requested (separate encrypted backup bucket, retention
policy, cross-region, proven restorability) — none of it existed at the time of this finding:
no AWS Backup plan or vault, no dedicated backup S3 bucket, no cross-region replication, no
on-demand DynamoDB backup ever taken. **Status (2026-11-08, later same day): fixed** — an AWS
Backup plan (`TravelMateBackupPlan`, `amplify/backend.ts`) with a KMS-encrypted vault now
covers every Data table plus the standalone `LoginAttempts` table, with a daily rule (35-day
retention) and a monthly rule (1-year retention, cold storage after 30 days) — confirmed live
via `GetBackupPlan`/`GetBackupSelection`. Cross-region replication deliberately **not** added:
not proportionate yet at this account's near-empty table sizes; revisit once there's real
traveller/partner data to protect. Restore capability is still **unverified** — no backup job
has run yet (the daily rule's first scheduled run is the next 05:00 UTC), and a restore has
never been drilled. That drill is a separate, explicit step (restoring into a new table name,
never over the live one) and still needs your go-ahead when you want it done.

### 7. Server-side upload content validation was missing — **Medium — FIXED**
`amplify/functions/submit-partner-application/handler.ts` and
`amplify/functions/update-partner-profile/handler.ts` only checked that an uploaded S3 key
*existed* (`HeadObjectCommand`), never inspecting its `ContentType`/`ContentLength` — so a
user calling the GraphQL mutation directly (bypassing the React form's client-side
extension/size checks) could reference any file type/size uploaded straight to their own S3
prefix. No code-execution path exists on uploaded content, but `profile-media/*` is
public-read and rendered back as `<img>`/`<S3Image>` to other users. **Implemented:** both
handlers now reject on `ContentType` outside an allow-list (`application/pdf`/`image/jpeg`/
`image/png` for certification docs, matching `JoinPage.tsx`'s existing client-side constants;
`image/jpeg`/`image/png`/`image/webp` for profile logo/cover) and `ContentLength` over 10MB,
before accepting the submission.

### 8. S3 bucket CORS is wildcarded — **Low-Medium → FIXED**
`GetBucketCors` on the partner-docs bucket returned `AllowedOrigins: ["*"]` at the time of this
finding. CORS doesn't substitute for the IAM/Cognito auth that already correctly gates who can
call S3 (not a direct account-takeover vector), but tightening it removes a cross-origin
avenue for driving a signed-in victim's authenticated requests against the bucket from any
page. **Status (2026-11-08, later same day): fixed** (`amplify/backend.ts`, CDK escape hatch
on `cfnBucket.corsConfiguration`) — `AllowedOrigins` now lists only
`https://www.travelmatevr.com`, `https://travelmatevr.com`,
`https://main.d1tgxuxxng291h.amplifyapp.com`, and `http://localhost:5173`; methods/headers/
exposed-headers/MaxAge kept identical to Amplify's own prior default. Confirmed live via
`GetBucketCors`.

### 9. Disposable/temporary email domains are not blocked at signup — **Low-Medium → FIXED**
No `PreSignUp` Lambda trigger existed on the User Pool at the time of this finding. **Status
(2026-11-08, later same day): fixed** — `amplify/functions/block-disposable-email/` is now
wired as the pool's `PreSignUp` trigger, rejecting sign-up (real email+password only, not
Google federation) when the email's domain matches a maintained list of ~65 known disposable-
mail providers. **Live-tested**: a real `SignUpCommand` against the deployed pool with
`tester@mailinator.com` was rejected (`UserLambdaValidationException`); an otherwise-identical
signup with a real domain and a strong password succeeded normally (then deleted as test
cleanup) — confirming the trigger blocks the right thing and nothing else.

### 10. Password policy is thin — **Low-Medium → FIXED**
Previously: 8-character minimum (raised to 12 earlier 2026-11-08, commit `04c021d`), no
composition requirements. **Status (2026-11-08, later same day): fully fixed** — the pool's
password policy (`amplify/backend.ts`) and the client-side check it must match
(`src/lib/security.ts`'s `isAcceptablePassword`, using Cognito's own documented symbol
character set so the two can't disagree) now both require at least one uppercase letter, one
lowercase letter, one number, and one symbol, on top of the 12–128 length bound. **Live-tested**
against the deployed pool: a weak password (`weakpassword`) was rejected
(`InvalidPasswordException: ... must have uppercase characters`); a strong password
(`GoodPassw0rd!23`) was accepted. No breached-password check (Cognito has no native support for
this — would need an app-layer call to the Pwned Passwords k-anonymity API); not implemented,
low priority, your call if you want it later.

### 11. Cognito Advanced Security (compromised-credential screening) unavailable — **Medium, informational**
The pool is on the Essentials feature tier; `AdvancedSecurityMode` (risk-based adaptive auth)
requires the Plus tier, which has its own pricing. Not recommending the upgrade unprompted —
noting it as an available option if you want native compromised-credential screening beyond
what the login-guard Lambda already does for brute-force.

### 12. S3 account-level Public Access Block not set — **Low → FIXED**
No account-level PAB configuration existed at the time of this finding — every individual
bucket already had all 4 PAB settings on, so this was a safety net for *future* buckets, not a
current exposure. **Status (2026-11-08, later same day): fixed** — confirmed live via
`GetPublicAccessBlock`, all 4 settings (`BlockPublicAcls`, `IgnorePublicAcls`,
`BlockPublicPolicy`, `RestrictPublicBuckets`) are now `true` at the account level.

### 13. WAF does not cover the CloudFront/Amplify Hosting distribution — **Low**
Discovered (and good news): WAF already protects the two sensitive surfaces —
`DataApiWaf` on the AppSync GraphQL API (500 req/5min/IP) and `LoginGuardWaf` on the Cognito
User Pool (100 req/5min/IP), both live-confirmed via `GetWebACLForResource`, built in
`amplify/backend.ts`. Only the static SPA shell itself (CloudFront) has no WAF — low severity
since it has no server-side logic to abuse beyond bandwidth/cost. Optional, not blocking.

  prior audit.
